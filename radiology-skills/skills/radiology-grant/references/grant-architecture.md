# Call-bound grant architecture

## First principle: logic blocks are not fixed headings

Build a proposal spine before prose, then place each block into the **current call's actual form**:

`need → verified gap → central question → hypothesis → aims → methods/decision rules → expected
inferences → significance/impact`

Do not impose an inherited “八股” outline on a form that intentionally leaves the research-content
structure open. A section map is valid only after the call passport records the mechanism, cycle,
official template/version and retrieval date.

For NSFC title/abstract/立项依据/研究内容/研究基础 development, also read
`nsfc-application-content-playbook.md`; it separates scientific functions from pseudo-rules and
programme-specific forms.

## 2026 NSFC operational snapshot — verify again for the live application

The official 2026 reform notice says NSFC is slimming applications, restructuring the General
Program and Young Scientists Fund (C) application framework, controlling total length, focusing on
core research content and innovation, and discouraging word-piling. For the 2026 General Program /
Young C form, the working snapshot is three main body blocks — **立项依据、研究内容、研究基础** —
with research content no longer forced into the older prescriptive sub-outline and a principle-based
30-page ceiling. Treat these details as `OFFICIAL_CYCLE_SNAPSHOT`, not timeless rules: verify them
against the live electronic form and the named programme before using or scoring them.

Therefore:

- do not require separate headings merely because an older application had them;
- do require the scientific functions below to be findable somewhere in the current form;
- report excess length or a missing field only after live verification;
- distinguish a missing **scientific function** from a missing legacy heading.

## Scientific functions every reviewer must locate

| Function | Reviewer question | Failure signal |
|---|---|---|
| Need and significance | Why is this problem consequential now? | prevalence/clinical rhetoric without a decision or knowledge gap |
| Scientific premise | What verified evidence makes the question worth testing? | selective citations, preliminary work without artifacts, planned work presented as evidence |
| Gap | What remains unknown, for whom and under what conditions? | “no one used model X” presented as a scientific gap |
| Central question | What single answer would change knowledge or practice? | a deliverables list or several unrelated questions |
| Hypothesis/logic | What result pattern would support or weaken the proposition? | unfalsifiable benefit claim |
| Aims | How does each aim answer part of the same question? | circular dependencies or a feature list |
| Approach | Can the inference be obtained without leakage or uncontrolled measurement shift? | method names without design, comparator or decision rule |
| Innovation | Which defensible increment changes the value of undertaking the work? | “first/leading/AI-enabled” without live gap evidence |
| Feasibility | Why can this team execute now? | availability asserted without counts, access, approvals or pilot artifacts |
| Impact/expected inference | What knowledge or decision changes if the work succeeds? | publications/models mistaken for scientific impact |
| Team/environment | Is the required expertise/infrastructure present for the proposed work? | prestige substituted for task-relevant capability |
| Budget/timeline/risk | Do resources and milestones map to aims and uncertainties? | round totals, hidden annotation/reader costs, no fallback |


## Aim architecture

Each aim must be interpretable even if another aim is unsuccessful unless the dependency is
scientifically essential and explicit. Use this order:

1. sub-question and hypothesis;
2. population/data and independent unit;
3. measurement/reference-standard contract;
4. comparator and analysis;
5. expected result **and disconfirming result**;
6. decision threshold or milestone;
7. fallback that still produces useful knowledge;
8. inference licensed by success and claim ceiling.

Avoid writing “Aim 1 build, Aim 2 optimize, Aim 3 validate” unless those activities test distinct
scientific propositions. Sequential software stages are not automatically scientific aims.

## Abstract / summary logic

Use the current form's actual constraints. Within them, make the whole loop visible:

```text
[consequential need] → [verified unresolved gap] → [central question and hypothesis] →
[coherent aims and distinguishing design] → [expected inference] → [bounded impact]
```

Do not insert unsupported novelty, performance numbers or feasibility claims to make the summary
sound decisive.

## Budget architecture

Budget follows aims and the current programme's verified budget regime. For each material item
record `aim → quantity × unit cost → timing → justification → fallback impact`.

Imaging proposals commonly omit acquisition/QC, contrast/tracer, core facility, de-identification,
storage/egress, annotation/adjudication, reader-study time, external validation, software/compute,
data-management and regulatory costs. Their omission is a feasibility defect even if the arithmetic
total is valid. Category names, caps, indirect costs and lump-sum/itemised requirements are live-call
rules; never infer them from a previous cycle.

## International mapping boundary

Map scientific functions, not headings. NIH, ERC, Wellcome and other funders make different
criteria and eligibility decisions. Read `international-grants.md`, then verify the named notice of
funding opportunity. A crosswalk is a drafting aid, not evidence of compliance or equivalence.
